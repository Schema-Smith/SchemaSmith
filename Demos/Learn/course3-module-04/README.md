# Course 3, Module 4 — Promotion & zero-downtime change (lab)

Goal: run the two operational disciplines that turn a converged schema into a *shippable* one.
First, **promotion** — build one artifact and deploy the **same package** to dev, then staging, then
prod, changing nothing but a handful of `SmithySettings_*` environment variables. Second, a
**zero-downtime column rename** done the safe way: rename `Customer.Email` to `Customer.ContactEmail`
through three separately-deployable, always-safe steps — **expand**, **backfill**, **contract** — so
the application never sees a missing column and you can stop between any two steps without breaking
anything.

The continuous example is the `OrdersService` spine — `Customer` and `OrderHeader` — exactly as
carried through Courses 2 and 3, including the **recyclebin** Module 3 installed (it rides along in the
package and gets promoted with everything else). Module 2 taught the script-token + env-var mechanics;
this module is about the *discipline* those mechanics make possible: build once, deploy everywhere, and
never take a column away in a single irreversible move.

## Layout

```
course3-module-04/
  package/<engine>/      the OrdersService artifact promoted dev -> staging -> prod
  expand/<engine>/       package/ + a nullable ContactEmail column added ALONGSIDE Email
  contract/<engine>/     Email dropped; the email index moved to ContactEmail
```

`<engine>` is `sqlserver`, `postgres`, `mysql`, or `mariadb`. Each folder carries its own `Package/` plus a
single shared **`base.settings.json`** — connection details and the package-path default. Everything
that varies per environment is injected as an env var at run time, identical to the Module 2 pipeline.

`package/` is the spine carried forward from Module 3:

- **`Customer`** — `CustomerId` (identity PK), `Name`, `Email`, `LoyaltyTier` (nullable, default
  `Standard`), with a non-unique index `IX_Customer_Email` on `Email`.
- **`OrderHeader`** — `OrderId` (identity PK), `CustomerId`, `OrderDate`, `TotalAmount`
  (`DECIMAL(10,2)`), with `FK_OrderHeader_Customer` into `Customer`.
- the **recyclebin** from Module 3 (the `recyclebin` registry table plus the `CustomTableDrop` /
  `CustomTableRestore` hooks and the cleanup job) — promotion deploys it to every environment. It isn't
  exercised in this module's flow (promotion and the column rename touch no table drops), but it travels
  with the artifact, which is the point: one package, the same everywhere.

| Engine | `CustomerId` | `Email` / `ContactEmail` | identity index name |
| ------ | ------------ | ------------------------ | ------------------- |
| SQL Server | `INT IDENTITY(1,1)` | `NVARCHAR(200)` | `IX_Customer_Email` |
| PostgreSQL | `INTEGER GENERATED BY DEFAULT AS IDENTITY` | `VARCHAR(200)` | `ix_customer_email` |
| MySQL | `INT AUTO_INCREMENT` | `VARCHAR(200)` | `IX_Customer_Email` |
| MariaDB | `INT AUTO_INCREMENT` | `VARCHAR(200)` | `IX_Customer_Email` |

*MariaDB is a fourth platform in the MySQL family — its own `Platform: MariaDb` selection and native
package, not the MySQL package retargeted. Its dialect matches MySQL except for a few DDL specifics
(invisible indexes, check-constraint drops, column-default reporting) that SchemaSmith handles for
you.*

## Part 1 — Promotion: one artifact, every environment

The package is **environment-agnostic**. `Product.json` declares a `TargetDb` script token
(defaulting to `ordersservice_dev`), and `Template.json`'s `DatabaseIdentificationScript` selects
that token instead of a hardcoded name. Override it per environment with
`SmithySettings_ScriptTokens__TargetDb`. Nothing else changes between dev, staging, and prod — same
package, same command.

Environment-variable mapping follows the standard convention: prefix `SmithySettings_`, and `__`
(double underscore) for nesting. So `ScriptTokens:TargetDb` -> `SmithySettings_ScriptTokens__TargetDb`,
`WhatIfONLY` -> `SmithySettings_WhatIfONLY`.

Pick an engine. The SQL Server form is shown — for **PostgreSQL**, **MySQL**, or **MariaDB**, swap
`sqlserver` for `postgres`, `mysql`, or `mariadb` in the `cd`. Everything else is identical.

```bash
cd package/sqlserver        # all three deploys run from here; only TargetDb changes

# 1. deploy to dev
SmithySettings_ScriptTokens__TargetDb=ordersservice_dev \
  schemaquench --ConfigFile:./base.settings.json

# 2. promote the SAME artifact to staging
SmithySettings_ScriptTokens__TargetDb=ordersservice_staging \
  schemaquench --ConfigFile:./base.settings.json

# 3. promote the SAME artifact to prod
SmithySettings_ScriptTokens__TargetDb=ordersservice_prod \
  schemaquench --ConfigFile:./base.settings.json
```

PowerShell equivalent:

```powershell
cd package\sqlserver
$env:SmithySettings_ScriptTokens__TargetDb = 'ordersservice_dev';     schemaquench --ConfigFile:.\base.settings.json
$env:SmithySettings_ScriptTokens__TargetDb = 'ordersservice_staging'; schemaquench --ConfigFile:.\base.settings.json
$env:SmithySettings_ScriptTokens__TargetDb = 'ordersservice_prod';    schemaquench --ConfigFile:.\base.settings.json
Remove-Item Env:SmithySettings_ScriptTokens__TargetDb
```

After all three runs, `Customer`, `OrderHeader`, `IX_Customer_Email`, and `FK_OrderHeader_Customer`
exist in every environment. **Re-run any one of them and it's a clean no-op** — every quench
converges to the declared state and stops. That idempotence is exactly what makes promoting the same
artifact across environments safe: the dev run, the staging run, and the prod run are the *same*
command pointed at different databases.

### Confirm promotion by hand

```bash
# SQL Server (repeat for ordersservice_staging / ordersservice_prod)
cd ../..                              # back to the lab folder
../lab-sql.sh sqlserver ordersservice_dev "SELECT name FROM sys.tables ORDER BY name; SELECT name FROM sys.indexes WHERE name='IX_Customer_Email'; SELECT name FROM sys.foreign_keys WHERE name='FK_OrderHeader_Customer'"

# PostgreSQL
../lab-sql.sh postgres ordersservice_dev "SELECT tablename FROM pg_tables WHERE schemaname='public' ORDER BY tablename; SELECT indexname FROM pg_indexes WHERE indexname='ix_customer_email'"

# MySQL
../lab-sql.sh mysql ordersservice_dev "SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA='ordersservice_dev' ORDER BY TABLE_NAME; SELECT DISTINCT INDEX_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='ordersservice_dev' AND INDEX_NAME='IX_Customer_Email'"

# MariaDB
../lab-sql.sh mariadb ordersservice_dev "SELECT TABLE_NAME FROM information_schema.TABLES WHERE TABLE_SCHEMA='ordersservice_dev' ORDER BY TABLE_NAME; SELECT DISTINCT INDEX_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='ordersservice_dev' AND INDEX_NAME='IX_Customer_Email'"
```

## Part 2 — Zero-downtime rename: expand / backfill / contract

You want to rename `Customer.Email` to `Customer.ContactEmail` on a live system. The naive move —
rename the column in one deploy — breaks every running app instance that still reads `Email` the
instant it lands. The safe pattern splits the rename into three deploys, each one safe to ship on its
own and safe to *pause* on:

1. **Expand** — add the new `ContactEmail` column **alongside** `Email`, nullable. Purely additive:
   nothing that reads `Email` is affected, and the column is nullable so existing rows are valid
   immediately. Deploy `expand/`, then roll the application out to write *both* columns.
2. **Backfill** — copy existing data forward: `ContactEmail = Email` for every row where it's still
   null. A plain data `UPDATE`, run once. Now both columns hold the same data.
3. **Contract** — once every app instance reads `ContactEmail` and nothing reads `Email`, drop
   `Email` and move the lookup index to the new column. Deploy `contract/`.

This lab runs all three against **`ordersservice_dev`** (the promotion in Part 1 already converged
dev to the `package/` state, which is the starting point `expand/` builds on).

### Step 1 — Expand (add ContactEmail alongside Email)

`expand/` is `package/` with one addition: `Customer` gains a nullable `ContactEmail` column. The
index is still on `Email` — expand changes nothing about how the column is read.

```bash
cd expand/sqlserver
SmithySettings_ScriptTokens__TargetDb=ordersservice_dev \
  schemaquench --ConfigFile:./base.settings.json
```

After this, the catalog shows **both** `Email` and `ContactEmail` on `Customer`, and
`IX_Customer_Email` is still present. Seed a row so the backfill has something to copy, then confirm:

```bash
# SQL Server — seed a Customer with an Email but no ContactEmail
cd ../..                              # back to the lab folder
../lab-sql.sh sqlserver ordersservice_dev "INSERT INTO dbo.Customer(Name, Email) VALUES('Ada Lovelace', 'ada@example.com')"

../lab-sql.sh sqlserver ordersservice_dev "SELECT Name, Email, ContactEmail FROM dbo.Customer"
```

`ContactEmail` reads `NULL` — the new column is there but empty. That's the expand state.

### Step 2 — Backfill (copy Email into ContactEmail)

The backfill is a one-time **data** step, not a schema change — so it's a plain `UPDATE`, not part of
any package. Run it once after expand:

```bash
# SQL Server
../lab-sql.sh sqlserver ordersservice_dev "UPDATE dbo.Customer SET ContactEmail = Email WHERE ContactEmail IS NULL"

# PostgreSQL
../lab-sql.sh postgres ordersservice_dev 'UPDATE public."Customer" SET "ContactEmail" = "Email" WHERE "ContactEmail" IS NULL'

# MySQL
../lab-sql.sh mysql ordersservice_dev "UPDATE Customer SET ContactEmail = Email WHERE ContactEmail IS NULL"

# MariaDB
../lab-sql.sh mariadb ordersservice_dev "UPDATE Customer SET ContactEmail = Email WHERE ContactEmail IS NULL"
```

Confirm the data copied — `ContactEmail` now equals `Email` for the seeded row:

```bash
../lab-sql.sh sqlserver ordersservice_dev "SELECT Name, Email, ContactEmail FROM dbo.Customer"
```

In production you'd run the backfill in batches for a large table and verify it before contracting.
Here one statement does it. With both columns now in sync, roll the application fully onto
`ContactEmail` so nothing reads `Email` anymore — *then* contract.

### Step 3 — Contract (drop Email, move the index)

`contract/` removes `Email` from `Customer` and renames the lookup index to `IX_Customer_ContactEmail`
on `ContactEmail`. **The index follows the column:** the email lookup still wants an index, so when the
data moves to `ContactEmail`, the index moves with it.

Dropping a column is destructive — preview it first. Run the same deploy with `SmithySettings_WhatIfONLY=true`
to see exactly what `contract/` will do without touching a row:

```bash
cd contract/sqlserver
# preview the destructive contract (changes NOTHING)
SmithySettings_ScriptTokens__TargetDb=ordersservice_dev \
SmithySettings_WhatIfONLY=true \
  schemaquench --ConfigFile:./base.settings.json
```

The preview reports the `Email` column drop and the index changeover. That drop is the line to read
twice — **dropping `Email` drops its data.** You already copied it into `ContactEmail` in Step 2, so
there's nothing to lose; the preview is where you confirm that before you pull the trigger. Then apply
it for real:

```bash
SmithySettings_ScriptTokens__TargetDb=ordersservice_dev \
  schemaquench --ConfigFile:./base.settings.json
```

After contract, the catalog shows `Email` **gone**, `ContactEmail` retaining the backfilled data,
`IX_Customer_Email` gone, and `IX_Customer_ContactEmail` present on `ContactEmail`:

```bash
# SQL Server
cd ../..                              # back to the lab folder
../lab-sql.sh sqlserver ordersservice_dev "SELECT name FROM sys.columns WHERE object_id=OBJECT_ID('dbo.Customer') ORDER BY name; SELECT name FROM sys.indexes WHERE object_id=OBJECT_ID('dbo.Customer') AND name LIKE 'IX_%'; SELECT Name, ContactEmail FROM dbo.Customer"

# PostgreSQL
../lab-sql.sh postgres ordersservice_dev "SELECT column_name FROM information_schema.columns WHERE table_name='Customer' ORDER BY column_name; SELECT indexname FROM pg_indexes WHERE tablename='Customer' AND indexname LIKE 'ix_%'"

# MySQL
../lab-sql.sh mysql ordersservice_dev "SELECT COLUMN_NAME FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='ordersservice_dev' AND TABLE_NAME='Customer' ORDER BY COLUMN_NAME; SELECT DISTINCT INDEX_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='ordersservice_dev' AND TABLE_NAME='Customer' AND INDEX_NAME LIKE 'IX_%'"

# MariaDB
../lab-sql.sh mariadb ordersservice_dev "SELECT COLUMN_NAME FROM information_schema.COLUMNS WHERE TABLE_SCHEMA='ordersservice_dev' AND TABLE_NAME='Customer' ORDER BY COLUMN_NAME; SELECT DISTINCT INDEX_NAME FROM information_schema.STATISTICS WHERE TABLE_SCHEMA='ordersservice_dev' AND TABLE_NAME='Customer' AND INDEX_NAME LIKE 'IX_%'"
```

### Why ContactEmail stays nullable

`contract/` keeps `ContactEmail` **nullable**, the same as it was in `expand/`. That's deliberate:
tightening it to `NOT NULL` would be a separate change that has to inspect every row first, and folding
it into the contract step would mix a constraint-tightening with the column drop. The safe, teachable
contract is "drop the old column, move the index" and nothing else. If you later want `ContactEmail`
not-null, that's its own expand/backfill-style step — verify no nulls remain, then tighten.

## A platform note on transactional DDL

The expand/backfill/contract split isn't just good hygiene — on MySQL and MariaDB it's a hard
requirement of how the engine applies DDL:

- **PostgreSQL** has fully transactional DDL — a failed multi-statement deploy can roll back as a unit.
- **SQL Server** runs most DDL transactionally, though a few statements can't participate in a user
  transaction.
- **MySQL** does **not** support transactional DDL — every DDL statement implicitly commits. There is
  no "undo the half-applied rename" on MySQL. Splitting the rename into three independently-committed
  quenches is *why* the pattern is safe here: each of expand, backfill, and contract is its own
  committed, converged state, so a failure between steps leaves the database in a known, valid
  intermediate state rather than a half-renamed one.
- **MariaDB** shares MySQL's lineage here too — no transactional DDL, every statement implicitly
  commits. The same expand/backfill/contract discipline applies for the same reason.

This is the deeper reason expand/contract is the right pattern everywhere, not just on MySQL/MariaDB: every
intermediate state (Email only → Email + ContactEmail → ContactEmail only) is a complete, valid schema
the application can run against. You can stop, deploy app code, and resume between any two steps.

## Re-run safely

Re-run any step and it converges and stops. Re-deploy `package/` after contracting and SchemaQuench
will see `Email` is back in the package and `ContactEmail` is not — it would reconcile toward
`package/` again. That's the point of declarative convergence: the package *is* the desired state, and
each quench moves the database to match it and no further.

## The principle

Two disciplines, one tool. **Promotion** is "build once, point the same artifact at each environment
with an env var, and let idempotent convergence make every deploy safe to repeat." **Expand /
backfill / contract** is "never take a column away in one move — add the new one, copy the data
forward, and only drop the old one once nothing reads it, previewing the destructive step with WhatIf
before you commit it." Both come down to the same SchemaSmith habit: declare the state you want, preview
the delta, and let the tool converge.
